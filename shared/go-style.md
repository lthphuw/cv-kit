# Go rules: full catalogue

This is cv-kit's complete rule set for Go, written for a long-running service that drives hardware over the network or
serial, such as a time-attendance terminal. It follows the Google Go Style Guide (its decisions and best practices,
paraphrased with attribution) and adds the concurrency, resource and device-I/O rules those documents treat only
briefly. `rules/go-style.md`, `rules/go-concurrency.md` and `rules/go-tests.md` are the short, always-loaded summaries
of this file; where they differ, this file wins.

**Rule format.** Each rule is one bullet: ID, strength, the rule, *Why*, *Check*, default *Severity*, and *Source*.
IDs are stable; never renumber, only append.

**Citing rules in findings.** Start every finding with the rule ID and the location, then say what is wrong and what
to do: `GO-CONC-9 poller.go:88: the stop case is a bare break inside select, so the loop never ends on shutdown; use
return or a labelled break`. Several hits of one rule in one file form one finding that lists the lines.

**Strength.**

- `[MUST]` / `[MUST NOT]`: breaking the rule is a finding. There is no "style preference" escape.
- `[PREFER]`: a judgement call. Report it only when the code is hard to read because of it, and then as Minor.
- Allowed exceptions are written inside the rule ("..., except in tests"). Nothing else is exempt.

**Precedence.**

1. A rule the project has written down (a style guide, CONTRIBUTING file, or a committed lint config) beats this
   catalogue for that project.
2. This catalogue.
3. `gofmt` output is never argued with. Where the Google guides are silent, follow the nearby code. Where a guide and a
   device-safety rule (GO-CONC, GO-EDGE, GO-RES) conflict, the safety rule wins; the Conflicts section says how.

**Severity.** The rule gives a default; rate each finding on its own effect and say why when you move it.

- **Critical**: the code can deadlock, crash, race, corrupt data, give wrong output, or leak a goroutine, memory,
  file or connection in a long-running process; or it lets one device or request stop the whole service.
- **Major**: a likely bug, a hazard for the next change, a risk that callers misuse the API, a measurable cost on a
  hot path, or missing tests for changed concurrent behaviour.
- **Minor**: naming, formatting, documentation, and rules that only change how equivalent code is spelled.

**Suppressions.** The only escape from a MUST rule is a suppression on the line that names the check and gives the
reason on the same line. Without the reason it is itself a finding (GO-TOOL-4).

**Check field.** `vet NAME` is an analyzer of `go vet` (checked against `go tool vet help`, Go 1.22.2). `staticcheck
CODE` is a code on the staticcheck checks page (read 2026-10-27); the ST codes are off by default. `gofmt` is a flag
of gofmt. `go test -race` is the race detector. `grep:` is a Perl-compatible pattern for `grep -nP` or `rg -nP`;
treat hits as candidates, not findings. `manual` means a reviewer has to read the code.

**Sources.** Each entry names its source by label. Section names are given where the source is a document; line
numbers are in the research note, which records the revision read for each.

## Tooling

- **GO-TOOL-1** [MUST] Every Go file is `gofmt` output. Formatter layout is never argued with. *Why:* one layout ends formatting noise in every diff. *Check:* `gofmt -l .` lists no file. *Severity:* Minor. *Source:* GGS "Formatting"; GGS "Line length".
- **GO-TOOL-2** [MUST] `go vet ./...` reports nothing, and no suppression hides a `copylocks`, `lostcancel`, `printf` or `atomic` finding. *Why:* these analyzers catch the lock copies, leaked contexts and misuse that corrupt data or leak in a long-running process. *Check:* `go vet ./...`. *Severity:* Major; a `copylocks` or `lostcancel` finding is Critical. *Source:* VET; EXP.
- **GO-TOOL-3** [PREFER] Run `gofmt -s` so repeated element types in slice and map literals are dropped. *Why:* one shorter form of the same literal, with nothing lost. *Check:* `gofmt -s -l .`. *Severity:* Minor. *Source:* GGD "Literal formatting".
- **GO-TOOL-4** [MUST] A suppression names the check and gives the reason on the same line; a suppression without a reason is a finding. *Why:* an unexplained suppression hides why a rule was broken, so the next reader cannot judge it. *Check:* grep: `nolint|lint:ignore` lines without a reason after them. *Severity:* Minor. *Source:* EXP (mirrors PY-LINT-3).
- **GO-TOOL-5** [PREFER] Enable the non-default staticcheck style checks (ST1000, ST1003, ST1016, ST1020, ST1021, ST1022) in the project's config, so the naming and documentation rules are checked by a tool. *Why:* the naming and documentation rules are checked only if a tool runs them. *Check:* read the project's staticcheck config. *Severity:* Minor. *Source:* SC (the checks page marks these non-default).

## GO-NAME: naming

- **GO-NAME-1** [MUST] Multi-word names are MixedCaps or mixedCaps, never with underscores, except test, benchmark and example function names, low-level OS or cgo shims, and file names. *Why:* one casing convention across the codebase. *Check:* grep: `^\s*(func|type|var|const)\s+\w*_\w*` (test, benchmark and example names are exempt); staticcheck ST1003 (non-default). *Severity:* Minor. *Source:* GGD "Underscores"; GGS "MixedCaps".
- **GO-NAME-2** [MUST] Constants are MixedCaps, with no ALL_CAPS and no `k` prefix (`MaxPacketSize`). *Why:* this matches the rest of Go naming. *Check:* staticcheck ST1003 (non-default). *Severity:* Minor. *Source:* GGD "Constant names".
- **GO-NAME-3** [MUST NOT] Do not name a constant after its value (`Twelve`), and do not define a constant that has no role beyond its value. *Why:* a value-derived name breaks when the value changes and says nothing about meaning. *Check:* read. *Severity:* Minor. *Source:* GGD "Constant names".
- **GO-NAME-4** [MUST] A package name is short, all lowercase, and made of letters and digits only; a third-party import whose package name breaks that is renamed at import. *Why:* the package name is the qualifier at every call site. *Check:* read; staticcheck ST1003 (non-default). *Severity:* Minor. *Source:* GGD "Package names".
- **GO-NAME-5** [MUST NOT] Do not name a package `util`, `common`, `helper`, `misc` or a similarly vague name; name it for what it provides. *Why:* call sites such as `helper.Marshal` say nothing about what happens. *Check:* manual; `find . -type d \( -name util -o -name common -o -name helper -o -name misc \)`. *Severity:* Minor. *Source:* GGB "Util packages"; GGD "Package names".
- **GO-NAME-6** [PREFER] Pick a package name that will not be shadowed by common local variables (`usercount`, not `count`) and that does not need renaming at import. *Why:* shadowing and renames hurt every use. *Check:* read. *Severity:* Minor. *Source:* GGD "Package names"; GGB "Shadowing".
- **GO-NAME-7** [MUST] Receiver names are one or two letters, an abbreviation of the type, and the same on every method of that type; never `this`, `self` or `_` (omit the name when unused). *Why:* predictable receivers keep docs and refactors cheap. *Check:* staticcheck ST1006 and ST1016 (ST1016 is non-default). *Severity:* Minor. *Source:* GGD "Receiver names".
- **GO-NAME-8** [MUST] Initialisms keep one case: `URL` or `url`, `ID` or `id`, `DB` or `db`; never `Url` or `Id`. *Why:* one spelling for every initialism. *Check:* staticcheck ST1003 (non-default). *Severity:* Minor. *Source:* GGD "Initialisms".
- **GO-NAME-9** [MUST NOT] Do not start a getter with `Get`, unless the concept is literally "get" (an HTTP GET). *Why:* the prefix is noise; name the noun. *Check:* grep: `func (\([^)]*\) )?Get[A-Z]`. *Severity:* Minor. *Source:* GGD "Getters".
- **GO-NAME-10** [PREFER] Name a function that blocks, calls a device, or does heavy work with a verb such as `Fetch` or `Compute`, so the call site shows that it may block or fail. *Why:* a reader can spot a hardware call at the call site. *Check:* read. *Severity:* Minor. *Source:* GGD "Getters".
- **GO-NAME-11** [MUST NOT] Do not shorten names by dropping letters (`Sbx` for `Sandbox`), especially exported names. *Why:* a dropped letter makes a name cryptic for every reader. *Check:* read. *Severity:* Minor. *Source:* GGD "Variable names".
- **GO-NAME-12** [PREFER] Leave out type words and repeated context: `users` not `userSlice`, `widget.New` not `widget.NewWidget`. *Why:* the type and the package already show the context, so the repetition adds nothing. *Check:* read. *Severity:* Minor. *Source:* GGD "Variable names", "Repetition".
- **GO-NAME-13** [PREFER] Use one name per concept within a package, and the same parameter name for the same concept. *Why:* one name per concept lets readers predict names across the package. *Check:* read. *Severity:* Minor. *Source:* GGS "Maintainability", "Consistency".

## GO-DOC: comments and documentation

- **GO-DOC-1** [MUST] Every exported name has a doc comment that is a full sentence starting with the name. *Why:* doc comments are what API users and IDEs show. *Check:* staticcheck ST1020, ST1021, ST1022 (non-default). *Severity:* Minor. *Source:* GGD "Doc comments".
- **GO-DOC-2** [MUST] Each package has exactly one package comment, directly above the `package` clause, in one file. *Why:* godoc shows exactly one package comment, so duplicates confuse readers. *Check:* staticcheck ST1000 (non-default). *Severity:* Minor. *Source:* GGD "Package comments".
- **GO-DOC-3** [MUST] Code that is deliberately complex (for example a buffer reused across a goroutine's lifetime) carries a comment saying why and what care it needs, plus a test or example of correct use. *Why:* the next maintainer must see the complexity is intended and must not "simplify" it into a bug. *Check:* read. *Severity:* Major. *Source:* GGS "Maintainability".
- **GO-DOC-4** [MUST] Document any cleanup the caller must perform (`Close`, `Stop`, cancel), and for a long-lived type the shutdown contract: which call stops it, whether it returns before the work has ended, and which call waits for that. *Why:* a caller who misses the cleanup leaks the resource; one who picks the wrong call loses in-flight work. *Check:* read. *Severity:* Major. *Source:* GGB "Documentation" (cleanup and shutdown contract).
- **GO-DOC-5** [MUST] Document thread-safety wherever it is not obvious: which methods may mutate, which lock internally, and what implementers of an interface must guarantee. *Why:* read-only calls are assumed safe and mutating ones unsafe, so only the exceptions need a note, and safety is part of the contract. *Check:* read. *Severity:* Major. *Source:* GGB "Documentation" (concurrency notes).
- **GO-DOC-6** [MUST] Document each interface people implement or call: its contract, its edge cases, the errors implementers may return, and its concurrency behaviour. *Why:* for a hardware port, the contract must say what a timeout and an empty read look like. *Check:* read. *Severity:* Minor. *Source:* GGB "Interfaces"; GGD "Interfaces".
- **GO-DOC-7** [PREFER] Explain why, not what; call out a nuance a reader may miss; drop comments that restate the code. *Why:* a comment that restates the code drifts from it, while the reason survives edits. *Check:* read. *Severity:* Minor. *Source:* GGS "Clarity".
- **GO-DOC-8** [PREFER] Document the sentinel errors and error types a function can return, so callers know which conditions they can handle. *Why:* callers can handle a condition only if they know it exists. *Check:* read. *Severity:* Minor. *Source:* GGB "Documentation".
- **GO-DOC-9** [PREFER] Show usage in a runnable example in a `_test.go` file rather than a long code block in a comment. *Why:* examples in test files are compiled and run with the tests, so they stay correct. *Check:* read. *Severity:* Minor. *Source:* GGB "Documentation" (examples); GGD "Examples".
- **GO-DOC-10** [PREFER] Document only the non-obvious parameters and options, and say why they matter, not every parameter. *Why:* a reader needs the non-obvious options, not a list that repeats the signature. *Check:* read. *Severity:* Minor. *Source:* GGB "Documentation".
- **GO-DOC-11** [PREFER] Use godoc formatting: a heading is one capitalised line without final punctuation; code is indented two spaces; paragraphs are separated by a blank line. *Why:* documentation reads well only when it follows the godoc conventions. *Check:* read. *Severity:* Minor. *Source:* GGB "Godoc formatting".

## GO-IMP: imports and packages

- **GO-IMP-1** [MUST] Rename an import only to resolve a name collision, and use the same local name for the same package everywhere. *Why:* stable names let readers recognise packages. *Check:* read. *Severity:* Minor. *Source:* GGD "Import renaming".
- **GO-IMP-2** [MUST] Group imports: standard library first, then other modules, then side-effect imports, with a blank line between groups. *Why:* a fixed order makes missing and duplicate imports obvious. *Check:* read (gofmt sorts within a group, not between groups). *Severity:* Minor. *Source:* GGD "Import grouping".
- **GO-IMP-3** [MUST NOT] Use blank imports (`import _ "pkg"`) in a library package. The exceptions are `main`, tests, and `embed`, which `//go:embed` needs. *Why:* a side effect hidden in a library blurs the dependency and blocks tests that need another import. *Check:* grep: `^\s*_\s+"`. *Severity:* Major. *Source:* GGD "Import blank".
- **GO-IMP-4** [MUST NOT] Do not use dot imports (`import . "pkg"`). *Why:* readers cannot tell where an identifier comes from. *Check:* grep: `^\s*\.\s+"`; staticcheck ST1001. *Severity:* Minor. *Source:* GGD "Import dot".
- **GO-IMP-5** [PREFER] Keep a coherent concept in one package, and split distinct concepts (for example the byte transport from the attendance protocol) into small packages. *Why:* callers import less, and internals need not be exported for coupling. *Check:* read. *Severity:* Minor. *Source:* GGB "Package size".
- **GO-IMP-6** [PREFER] Keep a library free of command-line code: the CLI is a thin client of the package, so the driver can be tested without it. *Why:* a file of thousands of lines and a swarm of tiny files are both hard to navigate. *Check:* read. *Severity:* Minor. *Source:* GGB "Complex command-line interfaces".

## GO-ERR: errors and failure

- **GO-ERR-1** [MUST] Signal failure with an `error` result, as the last result. *Why:* callers rely on the convention that the error comes last. *Check:* read. *Severity:* Minor. *Source:* GGD "Returning errors".
- **GO-ERR-2** [MUST NOT] Do not return a non-error value next to a non-nil error unless the function documents it. *Why:* a value beside an error is a zero value by habit only, and callers read it. *Check:* read. *Severity:* Major. *Source:* GGD "Returning errors".
- **GO-ERR-3** [MUST] An exported function returns the `error` interface, never a concrete error type such as `*os.PathError`. *Why:* a nil concrete pointer stored in an interface is a non-nil error, so callers see a failure that did not happen. *Check:* grep: `^func .*\)\s*\*?\w*Error\b`; read. *Severity:* Major. *Source:* GGD "Returning errors".
- **GO-ERR-4** [MUST] A function that takes a `context.Context` returns an `error`, so callers learn that cancellation stopped it and do not mistake a partial result for a full one. *Why:* a call that can be cancelled must say so, not return a silent partial result. *Check:* read. *Severity:* Major. *Source:* GGD "Returning errors".
- **GO-ERR-5** [MUST] Error strings start lowercase, unless they begin with a proper noun, acronym or exported name, and do not end with punctuation. *Why:* errors are embedded in larger messages. *Check:* staticcheck ST1005. *Severity:* Minor. *Source:* GGD "Error strings".
- **GO-ERR-6** [MUST NOT] Do not discard an error with `_` unless it is handled, returned, or justified in a comment. *Why:* a swallowed device or I/O error leaves the service running on a state that is false. *Check:* grep: `\b_\s*(:)?=\s*\w.*\(` on calls that return errors; read. *Severity:* Major. *Source:* GGD "Handle errors"; GGB "Error handling".
- **GO-ERR-7** [MUST] An error that is deliberately ignored gets a comment saying why that is safe. *Why:* a reader cannot tell a deliberate ignore from a mistake without the reason. *Check:* read. *Severity:* Minor. *Source:* GGD "Handle errors".
- **GO-ERR-8** [MUST NOT] Do not both log an error and return it from the same function; return it and let the caller choose to log, retry, rate-limit or stop. *Why:* logging at each layer floods the log with one failure repeated. *Check:* read. *Severity:* Major. *Source:* GGB "Logging errors".
- **GO-ERR-9** [MUST NOT] Do not signal failure or "not found" in-band with `-1`, an empty string, or `nil`; return an extra `error` or `bool` result. *Why:* an unchecked sentinel flows on and blames the wrong function. *Check:* read. *Severity:* Major. *Source:* GGD "In-band errors".
- **GO-ERR-10** [MUST] Handle an error first and return; keep the normal path unindented, and do not follow a return with `else`. *Why:* the success path is easiest to read when it is not nested. *Check:* read. *Severity:* Minor. *Source:* GGD "Indent error flow".
- **GO-ERR-11** [MUST] An error that callers must tell apart has a comparable identity (a sentinel value or a typed error), and its tests assert that identity, never the message text. *Why:* a comparable identity survives rewording; text matching breaks when a message changes. *Check:* grep: `err\.Error\(\)\s*==`; read. *Severity:* Major. *Source:* GGB "Error structure".
- **GO-ERR-12** [PREFER] Test a wrapped error with `errors.Is` or `errors.As`, not `==` or `errors.Unwrap`. *Why:* `==` misses a wrapped error, and `errors.Unwrap` does not handle an error that wraps several. *Check:* vet errorsas (misuse of `As`); read for `==`. *Severity:* Major. *Source:* GGB "Error structure".
- **GO-ERR-13** [PREFER] Put what callers need (a device address, a command code, a failing path) in fields of an error type, not only in its message. *Why:* callers can read a field without parsing the message. *Check:* read. *Severity:* Minor. *Source:* GGB "Error structure".
- **GO-ERR-14** [PREFER] Add to an error only what the wrapped error does not already say; return it unchanged rather than wrapping it with "failed". *Why:* the wrapper adds length and no information when the wrapped error already says it. *Check:* read. *Severity:* Minor. *Source:* GGB "Adding information to errors".
- **GO-ERR-15** [PREFER] Wrap with `%w` only when callers are meant to inspect the cause and the package documents that; use `%v` to annotate, to log, or to hide the cause. *Why:* `%w` makes the cause part of your API. *Check:* read. *Severity:* Major. *Source:* GGB "Placement of %w in errors".
- **GO-ERR-16** [PREFER] At the hardware boundary (serial or network driver), translate driver errors into the service's own error values: offline, timeout, rejected. *Why:* callers care about the outcome, and a raw driver error leaks transport detail into the API. *Check:* read. *Severity:* Major. *Source:* GGB "Error structure", "Adding information to errors" (boundary guidance adapted).
- **GO-ERR-17** [MUST NOT] Library code does not panic or exit the process on a per-device or transient failure (timeout, bad frame, dropped link); it returns an error. *Why:* one flaky device must not stop the service that serves the others. *Check:* grep: `panic\(|os\.Exit|log\.(Fatal|Panic)` outside `main`; read. *Severity:* Critical. *Source:* GGB "When to panic"; GGD "Don't panic".
- **GO-ERR-18** [PREFER] Use `panic` only for a broken invariant in the program's own code, never for bad input or a device failure. *Why:* a panic signals a bug; a device failure is ordinary and must be handled as an error. *Check:* read. *Severity:* Major. *Source:* GGB "When to panic"; GGD "Don't panic".
- **GO-ERR-19** [MUST NOT] Do not call a `Must`-style helper (one that panics or exits on failure) on runtime input such as device frames, payloads or requests; use it only for constants at start-up or in package initialisation. *Why:* a panic caused by external input is a remote crash. *Check:* grep: `\bmust?[A-Z]\w*\(`, then read the arguments. *Severity:* Critical. *Source:* GGD "Must functions".
- **GO-ERR-20** [PREFER] Name a helper that panics or exits on failure `MustXxx` or `mustXxx`, so its name shows it can stop the program. *Why:* the prefix tells the reader that the call can stop the program. *Check:* read. *Severity:* Minor. *Source:* GGD "Must functions".
- **GO-ERR-21** [PREFER] Recover a panic only at the boundary the design names (GO-CONC-10), never inside library code; a recover that stays documents what state it resets. *Why:* the farther a recover is from the panic, the less is known about held locks and half-done work. *Check:* grep: `recover\(\)`; read. *Severity:* Major. *Source:* GGB "Program checks and panics"; SPEC "Handling panics".
- **GO-ERR-22** [MUST NOT] Do not let a panic that is used for control flow cross a package boundary. The public entry point recovers it, returns an error, and re-panics anything that is not the package's own panic type. *Why:* callers must never see a panic as part of the API, and a foreign panic hidden as an error masks a real bug. *Check:* grep: `recover\(\)` in exported functions; read. *Severity:* Major. *Source:* GGB "When to panic" (parser pattern).
- **GO-ERR-23** [PREFER] Start-up errors (bad flags, bad configuration, a device unreachable at boot) are returned to `main`, which prints a message that says how to fix it and exits non-zero. *Why:* an actionable message helps the operator more than a stack trace. *Check:* read. *Severity:* Major. *Source:* GGB "Program initialization".
- **GO-ERR-24** [PREFER] Log a repeating failure once per change of state, or rate-limited, never on every poll. *Why:* a device that stays offline would otherwise write one line per poll, forever. *Check:* read. *Severity:* Major. *Source:* GGB "Logging errors".
- **GO-ERR-25** [MUST NOT] Do not log personal or biometric data: an employee's identity with a biometric template, a card number, or a raw fingerprint or face record. *Why:* log destinations are rarely fit to hold it. *Check:* grep: `(?i)log|slog|Print` near `finger|face|biometric|card|template`; read. *Severity:* Major. *Source:* GGB "Logging errors" (sensitive data); EXP (the identifiers are this domain's).
- **GO-ERR-26** [MUST NOT] `log.Fatal`, `log.Fatalf`, `log.Panic`, and `os.Exit` are called only from `main`. `log.Fatal` calls `os.Exit(1)`, so deferred calls, such as closing a serial port, do not run. *Why:* `log.Fatal` calls `os.Exit`, so deferred cleanup such as closing a serial port never runs. *Check:* grep: `log\.(Fatal|Panic)|os\.Exit`; read. *Severity:* Major. *Source:* STD `log.Fatal` (calls `os.Exit`); GGD "Don't panic".

## GO-LANG: language

- **GO-LANG-1** [MUST NOT] Do not copy a value whose methods are declared on a pointer, or a struct from another package that holds internal state (copying a `bytes.Buffer` makes a copy that aliases its storage). *Why:* a copy can alias or split internal state, so later calls misbehave. *Check:* vet copylocks for locks; read otherwise. *Severity:* Major. *Source:* GGD "Copying".
- **GO-LANG-2** [MUST] A method that changes its receiver has a pointer receiver. A slice receiver is a value only when the method neither reslices nor reallocates it. *Why:* a value receiver silently drops the change. *Check:* read. *Severity:* Major. *Source:* GGD "Receiver type".
- **GO-LANG-3** [PREFER] Use value receivers for maps, functions, channels, and small plain-data types with no mutable fields. *Why:* these values are already cheap to copy, and the value form shows that nothing changes. *Check:* read. *Severity:* Minor. *Source:* GGD "Receiver type".
- **GO-LANG-4** [PREFER] Use pointer receivers for large structs, for structs holding pointers to mutable state, and whenever the type may grow. *Why:* a pointer receiver keeps mutation explicit and survives growth. *Check:* read. *Severity:* Minor. *Source:* GGD "Receiver type".
- **GO-LANG-5** [PREFER] All methods of one type use the same receiver kind. *Why:* mixed receiver kinds confuse readers and interface satisfaction. *Check:* read. *Severity:* Minor. *Source:* GGD "Receiver type".
- **GO-LANG-6** [MUST] Name the fields in a composite literal of a struct type from another package. *Why:* field order and the full field set are not public API. *Check:* vet composites. *Severity:* Major. *Source:* GGD "Literal formatting".
- **GO-LANG-7** [PREFER] Build a value in one composite literal rather than field by field, and leave out zero-value fields when nothing is lost. *Why:* one literal reads more clearly than a sequence of assignments. *Check:* read. *Severity:* Minor. *Source:* GGD "Literal formatting".
- **GO-LANG-8** [MUST NOT] Do not end a `switch` clause with an unlabelled `break`; a Go clause already stops, so the `break` is noise and misleads inside a loop. *Why:* a `break` at the end of a clause does nothing and misleads readers inside a loop. *Check:* staticcheck S1023. *Severity:* Minor. *Source:* GGD "switch and break".
- **GO-LANG-9** [MUST] Loop variables: a closure or goroutine may capture a loop variable only in a file whose Go version (the `go` line in `go.mod`) is 1.22 or newer, and only for a variable declared in the `for` clause. In an older module, pass a copy as an argument or re-declare it in the body. *Why:* before 1.22 every iteration shares one variable, so every goroutine sees the last value; the compiler gates the new behaviour on the file's version. *Check:* vet loopclosure (it reports only in files older than Go 1.22); `go test -race`. *Severity:* Critical. *Source:* REL122 ("References to loop variables"); CMP `distinctVars` (`is122` from the file version); verified by a probe (`[3 3 3]` under `go 1.21`, `[0 1 2]` under `go 1.22`).
- **GO-LANG-10** [PREFER] Write `type T1 T2` for a new type; use an alias `type T1 = T2` only to migrate code between packages. *Why:* an alias creates no new type and is rarely the right choice. *Check:* read. *Severity:* Minor. *Source:* GGD "Type aliases".
- **GO-LANG-11** [PREFER] Print strings in messages with `%q`, so an empty string or control characters from a device stay visible. *Why:* empty strings and control characters from a device stay visible. *Check:* read. *Severity:* Minor. *Source:* GGD "Use %q".
- **GO-LANG-12** [PREFER] Write `any` in new code instead of `interface{}`. *Why:* `any` is an alias of `interface{}` since Go 1.18, so it is shorter and interchangeable. *Check:* read. *Severity:* Minor. *Source:* GGD "Use any".
- **GO-LANG-13** [PREFER] Use generics only for a real need, and start from the one concrete type in use. *Why:* polymorphism is easy to add later; unneeded abstraction is hard to remove. *Check:* read. *Severity:* Minor. *Source:* GGD "Generics".
- **GO-LANG-14** [MUST NOT] Do not use generics to build a domain-specific language, an error-handling framework or an assertion library. *Why:* such frameworks burden readers and give worse failure messages than standard practice. *Check:* read. *Severity:* Minor. *Source:* GGD "Generics".
- **GO-LANG-15** [PREFER] Keep a long function signature on one line and shorten a long call with local variables rather than wrapping; do not wrap an `if`, `for` or `switch` line. *Why:* a wrapped signature looks like part of the body, and a wrapped condition aligns with the block. *Check:* read. *Severity:* Minor. *Source:* GGD "Function formatting", "Conditionals and loops".
- **GO-LANG-16** [PREFER] Put the variable on the left and the constant on the right of a comparison. *Why:* a comparison reads better with the variable first. *Check:* read. *Severity:* Minor. *Source:* GGD "Conditionals and loops".
- **GO-LANG-17** [PREFER] Build a string in a loop with `strings.Builder`; join a few strings with `+`; use `fmt.Sprintf` for formatted text and `fmt.Fprintf` straight to a writer. *Why:* repeated concatenation in a loop is quadratic in the length. *Check:* read. *Severity:* Minor, Major on a documented hot path. *Source:* GGB "String concatenation".
- **GO-LANG-18** [PREFER] Prefer the core language and the standard library before a new dependency or custom machinery, and add no abstraction that nothing uses. *Why:* every extra mechanism is complexity that someone must learn and keep. *Check:* read. *Severity:* Minor. *Source:* GGS "Simplicity", "Least mechanism".
- **GO-LANG-19** [PREFER] Keep a helper from hiding a critical step or an edge case that a later edit could miss. *Why:* a hidden step is one that a later edit can miss. *Check:* read. *Severity:* Minor. *Source:* GGS "Clarity".

## GO-VAR: declarations and zero values

- **GO-VAR-1** [PREFER] Declare an empty local slice as `var s []T`: a nil slice is safe with `len`, `range` and `append`. *Why:* a nil slice is safe with `len`, `range` and `append`, so an empty value needs no allocation. *Check:* read. *Severity:* Minor. *Source:* GGD "Nil slices".
- **GO-VAR-2** [MUST NOT] Do not design an API that makes callers tell a nil slice from an empty one; report failure with an error. *Why:* a silent difference between nil and empty changes behaviour that callers then depend on. *Check:* read. *Severity:* Major. *Source:* GGD "Nil slices".
- **GO-VAR-3** [MUST] Initialise a map with `make` or a literal before the first write. Reading from a nil map is fine; writing to one panics. *Why:* a write to a nil map panics at run time, in code that tests often do not reach. *Check:* staticcheck SA5000. *Severity:* Critical. *Source:* GGB "Declaring variables with zero values" (must be initialised); runtime panic "assignment to entry in nil map" (Go 1.22.2 `runtime/map.go`).
- **GO-VAR-4** [PREFER] Use `var x T` or `new(T)` for a value that is ready to be filled; use a composite literal only when you know the initial contents. *Why:* an explicit zero literal adds noise and says nothing more. *Check:* read. *Severity:* Minor. *Source:* GGB "Declaring variables with zero values", "Composite literals".
- **GO-VAR-5** [MUST NOT] Do not use `:=` in an inner block to create a variable that shadows an outer one the code after the block must see, such as a `ctx` that carries a deadline. The deadline silently fails to apply. *Why:* the inner variable vanishes at the block end, so the code still compiles and silently drops the deadline. *Check:* read; the shadow analyzer is not part of the default `go vet`. *Severity:* Critical. *Source:* GGB "Shadowing".
- **GO-VAR-6** [PREFER] Reusing a name with `:=` to narrow a value (for example a context with a timeout) is fine when the wider value is no longer needed. *Why:* the wider value is then unreachable by accident, which is the point. *Check:* read. *Severity:* Minor. *Source:* GGB "Shadowing".
- **GO-VAR-7** [MUST NOT] Do not name a variable after a package that is still used in that scope (such as `url`). *Why:* the package's functions become unreachable in the shadowed scope. *Check:* read. *Severity:* Minor. *Source:* GGB "Shadowing".
- **GO-VAR-8** [PREFER] Give `make` a capacity only for a size that is known or measured. *Why:* an over-sized preallocation wastes memory in a process that runs for months. *Check:* read. *Severity:* Minor. *Source:* GGB "Size hints".

## GO-FN: functions

- **GO-FN-1** [PREFER] Name results only when two or more share a type, when the caller must act on one (a cancel function), or when a deferred function changes one. *Why:* a named result documents what the caller gets; an unnamed one makes the reader guess. *Check:* read. *Severity:* Minor. *Source:* GGD "Named result parameters".
- **GO-FN-2** [MUST] Use naked returns only in small functions. *Why:* naked returns in a long function hide what is returned. *Check:* read. *Severity:* Minor. *Source:* GGD "Named result parameters".
- **GO-FN-3** [PREFER] For many optional inputs, use an options struct passed last; split a long parameter list of same-typed values (timeouts, ports, retry counts) that are easy to swap. *Why:* long lists of same-typed arguments are easy to swap, and optional inputs need defaults. *Check:* read. *Severity:* Minor. *Source:* GGB "Option structure".
- **GO-FN-4** [MUST NOT] Do not put a `context.Context` in an options struct; pass it as its own parameter. *Why:* a context stored in an options struct outlives the call it was made for. *Check:* read. *Severity:* Major. *Source:* GGB "Option structure".
- **GO-FN-5** [PREFER] Use variadic functional options only when most callers need none and each option takes a value; apply defaults first and let the last duplicate win. *Why:* value-taking options let callers choose settings without rebuilding the argument list. *Check:* read. *Severity:* Minor. *Source:* GGB "Variadic options".
- **GO-FN-6** [PREFER] Pass a value that is a string or an interface directly, not through a pointer. *Why:* a pointer to a small value adds a nil risk and no gain. *Check:* read. *Severity:* Minor. *Source:* GGD "Pass values".
- **GO-FN-7** [PREFER] Do not hide a critical step in a helper where a later change could miss it. *Why:* a helper that hides a step is easy to miss when the code changes. *Check:* read. *Severity:* Minor. *Source:* GGS "Clarity".

## GO-IFACE: interfaces

- **GO-IFACE-1** [PREFER] Add an interface only for a real need: a second implementation, a test double the consumer owns, or an import cycle to break. Name it for the behaviour, not an abstract role. *Why:* an interface with one implementation adds indirection and nothing else. *Check:* read. *Severity:* Minor. *Source:* GGD "Interfaces"; GGB "Avoid unnecessary interfaces".
- **GO-IFACE-2** [PREFER] Define an interface in the package that uses it, list only the methods it calls, and keep it unexported unless outsiders implement it. *Why:* exporting an interface commits you to maintain it. *Check:* read. *Severity:* Minor. *Source:* GGD "Interfaces"; GGB "Interface ownership and visibility".
- **GO-IFACE-3** [PREFER] Keep interfaces small. *Why:* a large interface is hard to implement and to use. *Check:* read. *Severity:* Minor. *Source:* GGB "Designing effective interfaces".
- **GO-IFACE-4** [PREFER] Accept interfaces as parameters and return concrete types; return an interface only when the type is chosen at run time, to break an import cycle, or to protect the type's invariants. *Why:* a concrete return keeps its full API for callers; hiding it without a reason limits them. *Check:* read. *Severity:* Minor. *Source:* GGD "Interfaces"; GGB "Designing effective interfaces".
- **GO-IFACE-5** [MUST NOT] Do not add a back door, or export a test double, only for tests; test through the real implementation's public API. *Why:* test-only surface becomes production API and is easy to misuse. *Check:* read. *Severity:* Minor. *Source:* GGD "Interfaces".

## GO-STATE: globals and initialisation

- **GO-STATE-1** [MUST NOT] Keep behaviour-controlling state in package-level variables, global registries, callback lists, or lazily built client singletons; pass dependencies explicitly. Constants, unobservable caches, and state with no external effect are exempt. *Why:* global state couples unrelated code and makes tests order-dependent; a lazily built, unguarded client is also a data race under concurrent callers. *Check:* grep: `^var\s` that holds a map, slice, client or channel; read. *Severity:* Major. *Source:* GGB "Global state".
- **GO-STATE-2** [PREFER] A package-level convenience API is a thin wrapper over an instance API, is used only from `main`, documents whether it may be called concurrently, and offers a reset. *Why:* callers who need isolation or a test can still build their own instance. *Check:* read. *Severity:* Minor. *Source:* GGB "Providing a default instance".
- **GO-STATE-3** [MUST NOT] Do not do I/O, failing work, or goroutine starts in `init()` or in a package-level variable initialiser; put it in a constructor that `main` or the caller invokes. *Why:* importers cannot control or test it, and a failure there cannot be reported as an error. *Check:* read each `func init`. *Severity:* Major. *Source:* GGB "Program initialization" (errors go to `main`); UBER "goroutine-init" (goroutines in init).

## GO-RES: resources and memory

- **GO-RES-1** [MUST] Release every resource with `defer` on the line after acquiring it: a file, a connection, a serial port, a lock, a timer, a ticker, a cancel function, a response body. *Why:* a manual release is missed on one return path, and in a service that never restarts that leak lasts forever. *Check:* read; vet lostcancel for cancel functions. *Severity:* Critical. *Source:* UBER "defer-clean"; GGB "When to panic" (cleanup inside a recover); EXP.
- **GO-RES-2** [MUST] Check the error from the call that acquires a resource before the `defer` that closes it. *Why:* a failed open can return an unusable value, and deferring its close can panic. *Check:* staticcheck SA5001. *Severity:* Major. *Source:* SC SA5001.
- **GO-RES-3** [MUST] Check the error from `Close` on a writer (a file, a serial port, a socket) whose buffered data must reach the device or the disk. *Why:* a failed flush reported only by `Close` is otherwise lost. *Check:* read. *Severity:* Major. *Source:* EXP.
- **GO-RES-4** [MUST] Read or close the body of every HTTP response on every path after `Do`, `Get` or `Post` returns no error. A body that is not both read to EOF and closed keeps its connection from being reused. *Why:* an unclosed body pins the connection and its goroutines, so file descriptors and memory grow with each request. *Check:* read. *Severity:* Critical. *Source:* STD `net/http` `Client.Do` (read to EOF and closed); STD `net/http` `Response.Body`.
- **GO-RES-5** [MUST] Build one `http.Client`, and its `Transport`, per process and reuse it; never build a client for each request. *Why:* the transport holds the cached connections, so a client per request leaks idle connections. *Check:* grep: `http\.Client\{` inside a function body; read. *Severity:* Critical. *Source:* STD `net/http` `Client` (the transport holds connections).
- **GO-RES-6** [MUST NOT] Do not use `http.Get`, `http.Post`, or `http.DefaultClient` for calls to devices or remote services. Use a client with `Timeout` set, or give every request a context with a deadline. *Why:* a zero `Timeout` means no timeout, so one dead peer blocks a goroutine forever. *Check:* grep: `http\.(Get|Post|DefaultClient)`; read. *Severity:* Critical. *Source:* STD `net/http` `Client.Timeout` ("A Timeout of zero means no timeout").
- **GO-RES-7** [MUST] Set `ReadHeaderTimeout` and `IdleTimeout` on every `http.Server`, and `ReadTimeout` and `WriteTimeout` unless the handlers manage their own deadlines. *Why:* a zero or negative value means no timeout, so a silent client holds a connection and a goroutine forever. *Check:* grep: `http\.Server\{`; read. *Severity:* Critical. *Source:* STD `net/http` `Server` timeouts.
- **GO-RES-8** [MUST NOT] A goroutine that outlives a handler does not use the handler's `r.Context()`. That context is cancelled when the client disconnects or the handler returns. *Why:* a handler's context is cancelled when the handler returns, so detached work acts on a dead request. *Check:* read. *Severity:* Major. *Source:* STD `net/http` `Request.Context`.
- **GO-RES-9** [MUST NOT] Do not keep a small slice of a large buffer for a long time without copying it; the slice keeps the whole backing array alive. *Why:* one retained slice pins a large buffer for the life of the process. *Check:* read. *Severity:* Major. *Source:* EXP.
- **GO-RES-10** [MUST] Put pointers, not values, into a `sync.Pool`. *Why:* storing a non-pointer value allocates on every `Put`, which defeats the pool. *Check:* staticcheck SA6002. *Severity:* Major. *Source:* SC SA6002.
- **GO-RES-11** [PREFER] Reuse buffers through a bounded free list (a buffered channel with non-blocking `select` for get and put) or a `sync.Pool`, and reset a buffer before reuse. *Why:* the pattern never blocks and caps retained memory; a buffer put back dirty leaks the last message into the next. *Check:* read. *Severity:* Minor. *Source:* EG "A leaky buffer"; the reset rule is EXP.
- **GO-RES-12** [MUST NOT] Do not ship a binary built with `-race` as the production service. The race detector costs several times the memory and run time. *Why:* the race detector costs several times the memory and run time, which a service cannot afford. *Check:* read the build script. *Severity:* Major. *Source:* RACE "Runtime Overhead".
- **GO-RES-13** [MUST] A function that hands the caller something to release (a cancel function, a closer, a stop function) names it in its signature and documents that the caller must call it. *Why:* a skipped release is a resource leak, the failure a long-running process must not have. *Check:* read. *Severity:* Major. *Source:* GGD "Named result parameters" (cancel functions); GGB "Documentation".

## GO-CONC: concurrency

### Goroutine lifetime and ownership

- **GO-CONC-1** [MUST] Every goroutine has a stop signal (a cancelled context, a closed input channel, or bounded work) and an owner that waits for it to finish before the owner returns or shuts down. *Why:* a goroutine with no exit keeps its stack, the objects it references, and any open resource until the process dies. *Check:* read each `go` statement for the stop signal and the wait; GO-TEST-26 catches leaks in tests. *Severity:* Critical. *Source:* GGD "Goroutine lifetimes"; UBER "goroutine-forget"; EG "Goroutines"; GMM "Goroutine destruction"; EXP.
- **GO-CONC-2** [MUST NOT] Do not start a goroutine per item with a bare `go f(item)` that has no stop signal and no completion tracking. *Why:* the count and the memory are unbounded when items keep arriving. *Check:* grep: `\bgo\s+\w` inside a `for` or `range` over external input; read. *Severity:* Critical. *Source:* GGD "Goroutine lifetimes"; UBER "goroutine-forget".
- **GO-CONC-3** [MUST] A function that starts goroutines waits for them (cancels, then joins with a `WaitGroup` or equivalent) before it returns, unless it hands them to a documented long-lived owner. *Why:* a goroutine that outlives its function leaks, and nothing can wait for it. *Check:* read. *Severity:* Critical. *Source:* GGD "Goroutine lifetimes" (the `Run` example); UBER "goroutine-exit".
- **GO-CONC-4** [MUST] A type that owns background goroutines has one method (`Close`, `Stop` or `Shutdown`) that signals them and returns only after they have exited. *Why:* callers cannot free the worker's resources or restart cleanly if shutdown is fire-and-forget. *Check:* read; the method must both signal and wait. *Severity:* Critical. *Source:* UBER "goroutine-init".
- **GO-CONC-5** [MUST] Start goroutines from `main` or from a constructor that its caller later stops, never from `init()` or a package-level variable initialiser. *Why:* an importer gets a goroutine it cannot stop, configure, or test. *Check:* grep: `go\s` inside `func init`; read. *Severity:* Major. *Source:* UBER "goroutine-init".
- **GO-CONC-6** [MUST] A goroutine signals completion with a `defer` as its first statement (`defer wg.Done()`, `defer close(done)`), so every return path, including an early error return, signals. *Why:* a signal at the end of the body is skipped by an early return, and the waiter blocks forever. *Check:* read. *Severity:* Critical. *Source:* UBER "goroutine-forget"; PB "Explicit cancellation".
- **GO-CONC-7** [MUST] Call `wg.Add` before the `go` statement, in the goroutine that spawns it, never inside the new goroutine. `sync.WaitGroup.Go` (Go 1.25 or newer) does both steps. *Why:* an `Add` inside the goroutine can run after `Wait` has started, so `Wait` returns early. *Check:* staticcheck SA2000; vet `waitgroup` (Go 1.25). *Severity:* Critical. *Source:* SC SA2000; STD `sync.WaitGroup` ("must happen before a Wait"); REL125 (`WaitGroup.Go`, the vet `waitgroup` analyzer).
- **GO-CONC-8** [PREFER] In a module whose `go` line is 1.25 or newer, start counted goroutines with `wg.Go(f)`. *Why:* it removes the chance of forgetting `Done` on an early return. *Check:* read. *Severity:* Minor. *Source:* REL125; STD `sync.WaitGroup.Go`.
- **GO-CONC-9** [MUST NOT] Do not reuse a `WaitGroup` for a second batch before every `Wait` of the first batch has returned, and never copy a `WaitGroup` after first use. *Why:* a reused group can release waiters early or panic. *Check:* vet copylocks for copies; read for reuse. *Severity:* Critical. *Source:* STD `sync.WaitGroup` (ordering of `Add` and `Wait`).
- **GO-CONC-10** [MUST] A goroutine with a long-running loop recovers its own panic at the top of its body, logs it with the device or job identity, and then stops or restarts only that unit of work. *Why:* a panic that is not recovered in any goroutine ends the whole program, so one bad frame from one device would stop every other device. *Check:* read each long-lived `go` body for a deferred `recover`. *Severity:* Critical. *Source:* SPEC "Handling panics" (an unrecovered panic terminates the program); EG "Recover" (recover in a server goroutine); STD `WaitGroup.Go` (a panic in `f` is re-raised, so the recover belongs inside `f`).

### Bounding work and memory

- **GO-CONC-11** [MUST] Bound the goroutines: acquire a slot, or hand work to a fixed pool of workers, before the `go` statement. Never start one unbounded goroutine per incoming event, device or request; use `errgroup.SetLimit` for a group. *Why:* a slow device makes goroutines pile up when input is faster than it is handled. *Check:* read; grep: `\bgo\s` inside loops over external input. *Severity:* Critical. *Source:* EG "Channels" (gate before `go`, fixed workers); PB "Bounded parallelism"; EGRP `Group.SetLimit`.
- **GO-CONC-12** [MUST] Release a semaphore slot with `defer` in the goroutine that took it. *Why:* a path that returns early without releasing it shrinks the pool permanently, and the service slowly stops accepting work. *Check:* read. *Severity:* Major. *Source:* EG "Channels" (corrected: the example releases without `defer`); GMM "Channel communication" (buffered channel as a semaphore).
- **GO-CONC-13** [MUST] Each worker pool has an explicit shutdown: the producer closes the work channel, workers leave on `range` or on a context check, and the owner waits for them. *Why:* a pool stopped only by a signal value leaks its workers on every restart. *Check:* read. *Severity:* Critical. *Source:* EG "Channels" (fixed-worker example, corrected to close and wait).
- **GO-CONC-14** [MUST] Each device runs in its own goroutine, or in a bounded pool, with its own context and its own bounded queue, so one slow or offline device cannot block the others or a shared lock. *Why:* one blocked device then blocks only itself. *Check:* read. *Severity:* Critical. *Source:* EG "Concurrency" (goroutines are cheap, blocking one does not stop others); EXP for the shared-lock half.
- **GO-CONC-15** [MUST] A queue or channel between goroutines has a stated capacity and a stated policy for when it is full: block with a deadline, drop the oldest, or drop the newest and count the drops. No unbounded slice is used as a queue. *Why:* when a consumer stalls, an unbounded queue grows until the process is killed. *Check:* read. *Severity:* Critical. *Source:* EG "Channels" (a bounded buffer that drops when full); PB; EXP.
- **GO-CONC-16** [MUST] A channel buffer is zero or one, unless the code states how its size is chosen, what stops it filling under load, and what happens when it is full. *Why:* a guessed size only moves the stall to a heavier load, and a full channel blocks every writer. *Check:* grep: `make\(chan [^,)]*,\s*[2-9]` and buffer sizes given as a name. *Severity:* Major. *Source:* UBER "channel-size".
- **GO-CONC-17** [MUST] A goroutine that reports one result to a caller that may have stopped waiting sends it on a channel with capacity 1, or selects on the caller's context, so the late send never blocks. *Why:* an unbuffered reply channel strands the worker forever once the caller has given up on a timed-out call. *Check:* read. *Severity:* Critical. *Source:* EG "Channels" (the reply channel); GMM "Channel communication" (buffered send does not wait for the receiver); UBER "channel-size".

### Channels

- **GO-CONC-18** [MUST] Every blocking send or receive in a long-lived goroutine sits in a `select` with `ctx.Done()`, a stop channel, or a timer case, and returns the context error when it stops. *Why:* a plain send or receive blocks until its peer appears, so a worker blocked that way can never be stopped. *Check:* read. *Severity:* Critical. *Source:* PB "Explicit cancellation"; STD `context` package ("Done" and the select example); SPEC "Send statements".
- **GO-CONC-19** [MUST NOT] Do not send on a channel after it has been closed, and do not close one twice; each is a run-time panic, and the panic ends the program. *Why:* a send on a closed channel panics, and the panic ends the whole process. *Check:* `go test -race`; read. *Severity:* Critical. *Source:* SPEC "Close" and "Send statements" (sending to or closing a closed channel panics); RACE "Unsynchronized send and close operations".
- **GO-CONC-20** [MUST] Only the owner of a channel's send side closes it, once, after every send is ordered before the close. With several senders, a separate goroutine closes the channel after a `WaitGroup` shows that all senders have finished. *Why:* closing early, or closing twice, is a bug in a pipeline. *Check:* read; `go test -race`. *Severity:* Critical. *Source:* PB "Fan-out, fan-in"; RACE "Unsynchronized send and close operations".
- **GO-CONC-21** [MUST] A goroutine that receives from a channel it does not own also selects on its own stop signal, unless the producer's close is guaranteed. *Why:* if the producer never closes the channel, the consumer waits forever. *Check:* read. *Severity:* Critical. *Source:* GGD "Goroutine lifetimes"; EXP.
- **GO-CONC-22** [MUST] In a `select` loop that reads a channel which may be closed, use the two-value receive (or `range`) and leave the loop when `ok` is false. *Why:* a receive on a closed channel completes at once with the zero value, so the loop spins at full CPU producing fake items. *Check:* read. *Severity:* Critical. *Source:* SPEC "Receive operator" (a receive from a closed channel yields the zero value).
- **GO-CONC-23** [MUST] Make every channel field with `make` before it is used. Sends, receives and `range` on a nil channel block forever, and `close(nil)` panics. Set a channel to nil only to disable one `select` case, and say so in a comment. *Why:* a send on a nil channel blocks forever, so a struct built without `make` gives a goroutine that never wakes. *Check:* read. *Severity:* Critical. *Source:* SPEC "Receive operator", "Send statements", "Close" (nil channel behaviour).
- **GO-CONC-24** [MUST] A `select` loop that must stop on shutdown has a case for the stop signal, and that case leaves the loop with `return` or a labelled `break`. A plain `break` inside `select` leaves only the `select`. *Why:* the loop keeps running after shutdown. *Check:* staticcheck SA4011; read. *Severity:* Critical. *Source:* SC SA4011; UBER "goroutine-forget"; GGD "switch and break" (the switch form of the same trap).
- **GO-CONC-25** [MUST NOT] Do not spin: no empty `for {}`, and no `select` with an empty `default` inside a loop. Block on a channel, a timer, or the context instead. *Why:* a spinning goroutine burns a CPU core and can starve the scheduler on a small device. *Check:* staticcheck SA5002, SA5004. *Severity:* Critical. *Source:* SC SA5002, SA5004; GMM "Incorrect synchronization" (busy waiting).
- **GO-CONC-26** [MUST NOT] Do not use a buffered channel as a handshake that the receiver has taken a value. Only an unbuffered channel gives that guarantee. *Why:* the memory model gives no guarantee about a receiver of a buffered send. *Check:* read. *Severity:* Major. *Source:* GMM "Channel communication" (unbuffered and buffered channels).
- **GO-CONC-27** [PREFER] Broadcast cancellation by closing one channel or cancelling one context, not by sending one signal per goroutine. *Why:* a receive on a closed channel returns at once, so one close reaches any number of goroutines. *Check:* read. *Severity:* Minor. *Source:* PB "Explicit cancellation".
- **GO-CONC-28** [PREFER] Switch a `select` case off by setting its channel variable to nil until the case should be live. *Why:* a nil channel is never ready, so the case is skipped without a busy loop. *Check:* read. *Severity:* Minor. *Source:* EXP.
- **GO-CONC-29** [PREFER] Hand ownership of data from one goroutine to another over a channel, and protect state that stays in one place with a mutex; pick one mechanism per piece of data. *Why:* "Do not communicate by sharing memory; instead, share memory by communicating" is advice, but it allows a mutex around a counter. *Check:* read. *Severity:* Minor. *Source:* EG "Sharing by communicating"; STD `sync.Mutex`.
- **GO-CONC-30** [PREFER] Let one goroutine own a changing state (a device session, a retry queue) and take requests on a channel, with a reply channel, instead of sharing the state under locks. *Why:* one owner needs no locks and its `select` can react to stop and timers in every state. *Check:* read. *Severity:* Minor. *Source:* EXP.
- **GO-CONC-31** [MUST NOT] Do not use `sync.Cond` where shutdown or a deadline must interrupt the wait; use a channel, and close it to broadcast. *Why:* `Cond.Wait` returns only when signalled, so no context can interrupt it. *Check:* read. *Severity:* Major. *Source:* STD `sync.Cond` (`Wait` returns only when woken).

### Locks and shared state

- **GO-CONC-32** [MUST] Take every lock with `defer mu.Unlock()` on the line after `mu.Lock()`, except a critical section of straight-line statements with no early exit and no call that can panic. *Why:* an unlock skipped by an early return leaves the lock held, and every later caller hangs. *Check:* staticcheck SA2001 (empty critical section) and SA2003 (deferred `Lock` where `Unlock` was meant); read. *Severity:* Critical. *Source:* UBER "defer-clean"; STD `sync.Mutex` (unlock of an unlocked mutex is a run-time error).
- **GO-CONC-33** [MUST] A mutex is a named field (`mu sync.Mutex`), not an embedded one, so `Lock` and `Unlock` are not part of the type's API. *Why:* an embedded lock exports `Lock` and `Unlock` to any caller. *Check:* read. *Severity:* Major. *Source:* UBER "mutex-zero-value", "struct-embed".
- **GO-CONC-34** [MUST NOT] Do not copy a value that holds a `Mutex`, `RWMutex`, `WaitGroup`, `Once` or `Cond` after first use; pass and store such types by pointer and give them pointer receivers. *Why:* the copy has its own lock state, so two goroutines believe they hold the same lock. *Check:* vet copylocks. *Severity:* Critical. *Source:* GGD "Copying"; STD `sync.Mutex` ("must not be copied after first use").
- **GO-CONC-35** [MUST NOT] Do not hold a mutex across anything that can block: device or network I/O, a channel operation, `time.Sleep`, an HTTP call, or a callback into code you do not control. Copy what you need under the lock, unlock, then do the slow part. *Why:* a slow device stalls every goroutine that needs the same lock. *Check:* read. *Severity:* Critical. *Source:* STD `sync.Mutex` (callers block until the lock is free); EXP.
- **GO-CONC-36** [MUST NOT] A method guarded by a lock does not return an internal map or slice; it returns a copy made while the lock is held. *Why:* the caller then reads or writes shared memory after the lock is released. *Check:* read; `go test -race`. *Severity:* Critical. *Source:* UBER "container-copy".
- **GO-CONC-37** [MUST] A map shared between goroutines is guarded by one mutex, or confined to one goroutine. Reading a map while another goroutine writes it is a data race, and races on maps can corrupt memory. *Why:* a map racing with a writer can yield garbage, not just a stale value. *Check:* `go test -race`; read. *Severity:* Critical. *Source:* GMM "Races on multiword data"; EXP.
- **GO-CONC-38** [MUST] Every variable that more than one goroutine touches, with at least one write, is protected by a mutex, a channel, or `sync/atomic`. No race is harmless, including races on a flag, a counter or a timestamp. *Why:* a data race is undefined behaviour under the memory model, and the compiler may reorder around it. *Check:* `go test -race`. *Severity:* Critical. *Source:* GMM "Data races" (definition and implementation freedom); RACE "Primitive unprotected variable".
- **GO-CONC-39** [MUST] Flags and counters shared between goroutines use the typed atomics (`atomic.Bool`, `atomic.Int64`), and every access is atomic. Never mix atomic and plain access to the same variable. *Why:* one plain read of an atomic variable is a race. *Check:* vet atomic; `go test -race`. *Severity:* Critical. *Source:* GMM "Data races"; UBER "atomic" (the guide uses a third-party package; cv-kit uses the standard library); STD `sync/atomic` types.
- **GO-CONC-40** [MUST] A 64-bit value used with the raw `sync/atomic` functions on a 32-bit target is 64-bit aligned, for example the first field of its struct. *Why:* a 32-bit ARM board is a common attendance-terminal target. *Check:* staticcheck SA1027. *Severity:* Critical. *Source:* SC SA1027.
- **GO-CONC-41** [PREFER] Use `sync.RWMutex` only where reads clearly dominate and a measurement shows the gain. *Why:* an RWMutex costs more than a Mutex and helps only when reads dominate. *Check:* read. *Severity:* Minor. *Source:* EXP.
- **GO-CONC-42** [MUST NOT] Do not take a read lock on an `RWMutex` again while the same goroutine holds one, and do not try to upgrade or downgrade a lock. *Why:* a waiting writer blocks new readers, so the second read lock deadlocks. *Check:* read. *Severity:* Critical. *Source:* STD `sync.RWMutex`.
- **GO-CONC-43** [MUST] Lazy one-time initialisation uses `sync.Once` or start-up code, never a hand-written flag check. Do not place an unbounded blocking call (connect, DNS) inside the `Once` function without a timeout. *Why:* a flag read without synchronisation can be seen as set while the data is not, and every other caller blocks until the first call returns. *Check:* `go test -race`; read. *Severity:* Critical. *Source:* GMM "Incorrect synchronization" (double-checked locking); GMM "Once".
- **GO-CONC-44** [MUST NOT] Do not wait for another goroutine by polling a plain variable. Wait on a `WaitGroup`, a channel or a lock, then read the results. *Why:* a poll on a plain variable can loop forever, and a goroutine's exit orders nothing. *Check:* `go test -race`. *Severity:* Critical. *Source:* GMM "Incorrect synchronization" (busy waiting; a goroutine's exit orders nothing).
- **GO-CONC-45** [MUST NOT] Do not share a result variable such as `err` between a goroutine and the goroutine that starts it; declare it inside the new goroutine with `:=`. *Why:* the outer and inner writes race, and the wrong result can be the one sent. *Check:* `go test -race`; read. *Severity:* Critical. *Source:* RACE "Accidentally shared variable".

### Context

- **GO-CONC-46** [MUST] A function that blocks, does I/O, or waits on a device takes `ctx context.Context` as its first parameter, honours its cancellation, and returns `ctx.Err()` when it stops early. *Why:* cancellation reaches the function only through its context, so the function must take one. *Check:* read. *Severity:* Critical. *Source:* GGD "Contexts"; GGD "Returning errors"; CB "Context"; STD `context` (Done).
- **GO-CONC-47** [MUST] Pass the caller's context down to every outgoing device, network or database call. Do not replace it with `context.Background()` midway. *Why:* a fresh root context never sees shutdown, so work started under it can leak. *Check:* grep: `context\.(Background|TODO)\(\)` outside `main`, `init` and tests. *Severity:* Critical. *Source:* GGD "Contexts" (when to use Background).
- **GO-CONC-48** [MUST NOT] Do not store a `context.Context` in a struct field. Add a context parameter to each method that needs one. *Why:* a stored context outlives the call it was made for, and its deadline goes stale. *Check:* grep: a `context.Context` field inside a struct body; read. *Severity:* Major. *Source:* GGD "Contexts"; STD `context` ("Do not store Contexts inside a struct type").
- **GO-CONC-49** [MUST NOT] Do not define a custom context type, or take a context-like interface other than `context.Context` in a signature. *Why:* custom types force conversions and block automated refactors. *Check:* read. *Severity:* Major. *Source:* GGD "Contexts".
- **GO-CONC-50** [MUST] Call the cancel function from `context.WithCancel`, `WithTimeout` and `WithDeadline` on every path, normally with `defer cancel()` on the next line. *Why:* an uncancelled context keeps its timer and its place in the parent until the parent ends, and a service-lifetime parent never does. *Check:* vet lostcancel. *Severity:* Critical. *Source:* STD `context` (cancel releases resources); CB "Derived contexts"; vet lostcancel reports a discarded cancel function.
- **GO-CONC-51** [MUST NOT] Do not pass a nil `context.Context`; use `context.TODO()` as a placeholder that is replaced before merge. *Why:* callees call methods on the context, and a nil one panics. *Check:* staticcheck SA1012. *Severity:* Major. *Source:* STD `context` (nil context); SC SA1012.
- **GO-CONC-52** [MUST NOT] Do not pass optional parameters or configuration through `context.WithValue`. Keys have an unexported type and typed accessors; a built-in type such as `string` is never a key. *Why:* built-in key types collide across packages, and hidden values are invisible to callers. *Check:* staticcheck SA1029; read. *Severity:* Major. *Source:* STD `context` (`WithValue`); SC SA1029; CB "Context".
- **GO-CONC-53** [MUST] Work that must outlive its caller is detached on purpose (`context.WithoutCancel`, Go 1.21 or newer) and gets its own timeout and owner. *Why:* the detached context never cancels, so unbounded detached work is a goroutine leak. *Check:* read. *Severity:* Major. *Source:* REL121 (`WithoutCancel`); STD `context.WithoutCancel`.
- **GO-CONC-54** [MUST] With `context.AfterFunc` or `time.AfterFunc`, `f` runs in its own goroutine, and `stop` returning false does not mean `f` has finished. Coordinate with `f` explicitly when the caller must wait. *Why:* shutdown that frees what `f` uses races with a still-running `f`. *Check:* read. *Severity:* Major. *Source:* STD `context.AfterFunc`, `time.Timer.Stop`; REL121 (`AfterFunc`).
- **GO-CONC-55** [MUST] Every loop or step that can block for a long time observes `ctx.Done()` (or a deadline) on each iteration. *Why:* cancellation is only a signal, and work stops only if the code looks at it. *Check:* read. *Severity:* Critical. *Source:* STD `context` (Done); GGD "Contexts".
- **GO-CONC-56** [MUST] Shut down in this order: stop taking new work, cancel the root context, wait for the goroutines with a bounded timeout, then close connections and files. Cancelling does not wait for work to stop. *Why:* a cancel function does not wait; skipping the wait lets goroutines touch closed resources. *Check:* read; a shutdown test (GO-TEST-24). *Severity:* Critical. *Source:* STD `context.CancelFunc` (does not wait); EXP for the order.
- **GO-CONC-57** [MUST] `main` derives its root context from `signal.NotifyContext`, for `os.Interrupt` and `syscall.SIGTERM`. *Why:* a service must stop cleanly on Ctrl-C and on a service-manager stop signal, with its goroutines and devices shut down. *Check:* read. *Severity:* Major. *Source:* STD `os/signal.NotifyContext`.
- **GO-CONC-58** [MUST] A channel passed to `signal.Notify` is buffered. A signal that arrives while an unbuffered channel is not ready is dropped. *Why:* a signal that arrives while an unbuffered channel is not ready is dropped. *Check:* staticcheck SA1017. *Severity:* Major. *Source:* SC SA1017; STD `os/signal.Notify`.

### Errgroups and fan-out

- **GO-CONC-59** [PREFER] Related subtasks that succeed or fail together use `errgroup.WithContext`; always call `Wait` and return its error. *Why:* the derived context is cancelled on the first error, so sibling tasks stop early. *Check:* read. *Severity:* Minor. *Source:* EGRP `WithContext`, `Group.Wait`.
- **GO-CONC-60** [MUST] Each function run by an errgroup watches the group context and returns when it is cancelled. `Wait` blocks until every function returns. *Why:* `Wait` blocks until every function returns, so one that ignores cancellation hangs the group. *Check:* read. *Severity:* Critical. *Source:* EGRP `Group.Wait`, `WithContext`.
- **GO-CONC-61** [MUST NOT] Do not use the context from `errgroup.WithContext` after `Wait` returns, and do not reuse a group for a different task. *Why:* the context is cancelled when `Wait` returns, and a group is meant for one task. *Check:* read. *Severity:* Major. *Source:* EGRP `WithContext`, `Group`.

### Blocking calls

- **GO-CONC-62** [MUST NOT] Do not run a blocking device call in the goroutine that handles shutdown or commands. Hand it to a worker that has a deadline. *Why:* one hung device would freeze shutdown and every command behind it. *Check:* read. *Severity:* Critical. *Source:* EXP.
- **GO-CONC-63** [MUST] A call that cannot take a context runs in its own goroutine and reports on a buffered channel. The caller waits in a `select` on that channel, the timeout, and the stop signal. *Why:* an abandoned call can then finish and exit without blocking. *Check:* read. *Severity:* Critical. *Source:* UBER "channel-size"; EXP.
- **GO-CONC-64** [MUST NOT] Do not `defer` inside an endless loop or a long-running loop body; move the body into a function, so its defers run each pass. *Why:* deferred calls run only when the function returns, so a long loop piles them up. *Check:* staticcheck SA5003 (defer in an infinite loop) and SA9001 (defer in a range loop); read. *Severity:* Critical. *Source:* SC SA5003, SA9001; EXP.
- **GO-CONC-65** [MUST NOT] Do not `time.Sleep` in a loop that must stop on shutdown. Wait with a timer or ticker in a `select` with `ctx.Done()`. *Why:* a sleeping goroutine cannot see a stop request until the sleep ends. *Check:* read `time.Sleep` inside loops of goroutines. *Severity:* Critical. *Source:* UBER "goroutine-forget"; STD `time.Sleep` (takes no context).
- **GO-CONC-66** [MUST NOT] Do not rely on `for range ticker.C`, or a bare `<-ticker.C`, as the only way out of a polling loop; select on the context as well. `Stop` does not close the channel. *Why:* `Stop` does not close the channel, so a goroutine blocked on it never wakes. *Check:* read. *Severity:* Critical. *Source:* STD `time.Ticker.Stop` and `time.Tick`.

## GO-EDGE: device I/O and long-running constraints

- **GO-EDGE-1** [MUST] Every network or serial read and write has a deadline (`SetDeadline`, `SetReadDeadline`, `SetWriteDeadline`), or is cancelled by closing the connection when its context ends. Refresh the deadline after each good operation when an idle timeout is wanted. *Why:* I/O to an unplugged or silent device otherwise blocks the goroutine for ever. *Check:* read each call on a `net.Conn` or a port; a serial driver's read timeout counts. *Severity:* Critical. *Source:* STD `net.Conn` (SetDeadline and its idle-timeout remark); EXP for serial ports.
- **GO-EDGE-2** [MUST] Every retry loop has a maximum number of attempts or a context, and waits between attempts. *Why:* a tight retry against a dead device burns CPU and floods the log. *Check:* read. *Severity:* Major. *Source:* EXP.
- **GO-EDGE-3** [MUST] Every map, slice, queue or cache that grows with device or network input has a cap and an eviction or reject policy. *Why:* a service that never restarts turns any unbounded growth into an outage. *Check:* read; grep: `append\(` inside long-lived loops. *Severity:* Critical. *Source:* EG "Channels" (bounded resources); EXP.
- **GO-EDGE-4** [MUST] A length read from a device frame or a network message is validated before it sizes an allocation. *Why:* a hostile or corrupt length can ask for gigabytes. *Check:* read. *Severity:* Critical. *Source:* EXP.
- **GO-EDGE-5** [MUST] Express durations as `time.Duration`. When a wire format or configuration forces a bare number, put the unit in the field name (`TimeoutMillis`). *Why:* a bare 10 is read as seconds in one place and milliseconds in another. *Check:* staticcheck SA1004. *Severity:* Major. *Source:* UBER "time"; SC SA1004.
- **GO-EDGE-6** [MUST] Measure elapsed time and timeouts with the monotonic clock: `time.Since`, or the subtraction of two `time.Now()` values. Use wall-clock time for timestamps only. *Why:* the wall clock can jump when the clock is synchronised. *Check:* read. *Severity:* Major. *Source:* STD `time` package ("Monotonic Clocks").
- **GO-EDGE-7** [MUST] Compare, add and subtract instants with `time.Time` methods; use `AddDate` for the same clock time on another day, and `Add(24*time.Hour)` for exactly 24 hours. *Why:* a calendar day is not always 24 hours, which shifts punch times around clock changes. *Check:* read. *Severity:* Major. *Source:* UBER "time".
- **GO-EDGE-8** [MUST] Exchange timestamps with devices and files as RFC 3339 with an explicit zone, unless another format is agreed and documented. *Why:* records from two devices are not comparable without a stated format and zone. *Check:* read. *Severity:* Major. *Source:* UBER "time".
- **GO-EDGE-9** [MUST] Read and write fixed-layout binary frames with `encoding/binary` and an explicit byte order, not by casting bytes to a struct. *Why:* an explicit byte order is the same on every machine; a struct cast is not. *Check:* grep: `"unsafe"`; read. *Severity:* Major. *Source:* EXP.
- **GO-EDGE-10** [MUST NOT] Do not use `unsafe` in production code to reinterpret frame bytes without a reviewed reason in a comment. *Why:* a cast of frame bytes to a struct depends on layout and alignment, which vary by platform. *Check:* grep: `"unsafe"`. *Severity:* Major. *Source:* EXP.
- **GO-EDGE-11** [MUST] With `go 1.23.0` or newer in `go.mod`, timers need no drain of `t.C` after `Stop` or `Reset`; an older module keeps the stop-then-drain pattern. *Why:* from Go 1.23 the timer channel is synchronous and no stale value is delivered after `Stop` or `Reset`. *Check:* read `go.mod`; staticcheck SA1025. *Severity:* Major. *Source:* REL123 "Timer changes" (applies when the main module's `go` line is 1.23.0 or later); STD `time.Timer.Stop`.
- **GO-EDGE-12** [MUST NOT] Do not test whether a timer has fired with `len` or `cap` of its channel; use a non-blocking `select`. *Why:* with the Go 1.23 behaviour both are always 0. *Check:* read. *Severity:* Major. *Source:* REL123 "Timer changes".
- **GO-EDGE-13** [MUST] Create periodic work with `time.NewTicker` and `defer ticker.Stop()`. Use `time.Tick` only for a ticker that lives as long as the process. *Why:* a ticker that is never stopped keeps firing and holds memory. *Check:* staticcheck SA1015. *Severity:* Major. *Source:* SC SA1015; STD `time.Tick` ("the underlying Ticker cannot be recovered by the garbage collector"); REL123.
- **GO-EDGE-14** [MUST NOT] In a module whose `go` line is older than 1.23.0, do not call `time.After` or `time.Tick` inside a loop or a hot path. Create one `Timer` or `Ticker` and `Reset` it. *Why:* before Go 1.23 an unfired timer is not freed until it fires, so each pass leaks one. *Check:* staticcheck SA1015; read. *Severity:* Major. *Source:* REL123 "Timer changes"; STD `time.After`.
- **GO-EDGE-15** [MUST] Stop an `http.Server` with `Shutdown(ctx)` under a deadline, and wait for it to return before the process exits. `Shutdown` and `Close` do not track hijacked connections such as WebSockets, so track those yourself. *Why:* exiting as soon as serving stops drops the in-flight requests. *Check:* read. *Severity:* Critical. *Source:* STD `net/http` `Server.Shutdown`, `Server.Close`.

## GO-TEST: tests

- **GO-TEST-1** [MUST] Write the failing test first and watch it fail for the right reason, as the working principles require. *Why:* a test that has never failed proves nothing about the change. *Check:* the engineer's test output shows the failure. *Severity:* Major. *Source:* PRIN "Test first".
- **GO-TEST-2** [MUST] Table-driven tests use `t.Run`, and each subtest runs on its own, with no dependence on another case's result or state. *Why:* a failing case then names itself, and the other cases still run. *Check:* `go test -run 'TestX/case'`. *Severity:* Major. *Source:* GGD "Subtests", "Table-driven tests".
- **GO-TEST-3** [PREFER] Name a subtest like an identifier: short, no spaces, no slashes; put a long description in a separate field and print it on failure. *Why:* slashes act as filter separators, and spaces are rewritten. *Check:* read. *Severity:* Minor. *Source:* GGD "Subtests".
- **GO-TEST-4** [MUST NOT] Do not identify a failing table row only by its index; print the inputs. *Why:* nobody wants to count table entries to find the failing case. *Check:* grep: `case #%d`; read. *Severity:* Minor. *Source:* GGD "Identify the input".
- **GO-TEST-5** [PREFER] Use one table when cases share logic; split into several test functions when cases need different logic. *Why:* per-row special logic makes a table hard to follow, and the table tends to grow. *Check:* read. *Severity:* Minor. *Source:* GGD "Table-driven tests".
- **GO-TEST-6** [MUST NOT] Do not choose a fake or a real dependency through a field and a `switch` inside a table row; write separate test functions that each set up their own dependency. *Why:* row-driven setup hides which dependency each case really used. *Check:* read. *Severity:* Minor. *Source:* GGD "Table-driven tests".
- **GO-TEST-7** [MUST] A helper that takes `*testing.T` calls `t.Helper()` first. *Why:* a failure points at the calling line instead of inside the helper. *Check:* read. *Severity:* Minor. *Source:* GGD "Test helpers".
- **GO-TEST-8** [MUST] A helper's parameters are ordered: context first, then `t`, then the rest. *Why:* helpers then read the same way as production functions. *Check:* read. *Severity:* Minor. *Source:* GGD "Contexts" (test helpers); GGD "Test helpers".
- **GO-TEST-9** [MUST NOT] Do not call `t.Fatal`, `t.FailNow` or `t.SkipNow` from a goroutine other than the test's own; use `t.Error` and return, or send the result back to the test goroutine. *Why:* these calls stop only the calling goroutine, so the test goes on and may pass wrongly. *Check:* vet testinggoroutine; staticcheck SA2002. *Severity:* Major. *Source:* GGB "Don't call t.Fatal from separate goroutines"; SC SA2002; VET testinggoroutine.
- **GO-TEST-10** [PREFER] Report each mismatch with `t.Error`, and use `t.Fatal` only where later checks would be meaningless, such as failed setup or an unexpected error. *Why:* the developer then fixes every failure in one pass. *Check:* read. *Severity:* Minor. *Source:* GGD "Keep going"; GGB "Error handling in test helpers", "t.Error vs. t.Fatal".
- **GO-TEST-11** [PREFER] Write a failure message as `Func(input) = got, want want`, with the input shown and the actual value before the expected one. *Why:* a failure should be diagnosable without opening the test source. *Check:* read. *Severity:* Minor. *Source:* GGD "Got before want", "Identify the function".
- **GO-TEST-12** [PREFER] Print strings with `%q` and small structs with `%+v` in failure messages. *Why:* quotes make empty or padded device strings visible. *Check:* read. *Severity:* Minor. *Source:* GGD "Use %q"; GGD "Level of detail".
- **GO-TEST-13** [PREFER] Compare a whole struct, slice or map in one deep comparison with `cmp.Diff`, and state the direction in the message (`(-want +got)`). *Why:* a reader cannot tell which side is which without a key. *Check:* read. *Severity:* Minor. *Source:* GGD "Full structure comparisons", "Print diffs".
- **GO-TEST-14** [PREFER] Use `cmp.Equal` or `cmp.Diff`, not `reflect.DeepEqual`. *Why:* `reflect.DeepEqual` is sensitive to unexported fields. *Check:* grep: `reflect\.DeepEqual` in `_test.go`. *Severity:* Minor. *Source:* GGD "Equality comparison and diffs".
- **GO-TEST-15** [MUST NOT] Do not import `github.com/google/go-cmp/cmp` in production code; it is for tests, and it may panic when it suspects misuse. *Why:* a panic in production code ends the process. *Check:* grep: `go-cmp` in a file that is not `_test.go`. *Severity:* Major. *Source:* GGD "Equality comparison and diffs".
- **GO-TEST-16** [MUST NOT] Do not decide which error came back by comparing its text in a test; use `errors.Is` or `errors.As`. *Why:* rewording an error message should not break a test. *Check:* grep: `err\.Error\(\)\s*==`, `strings\.Contains\(err`. *Severity:* Minor. *Source:* GGD "Test error semantics".
- **GO-TEST-17** [PREFER] Register teardown of a fake, a listener or a temporary file with `t.Cleanup` in the helper that creates it. *Why:* cleanup then runs when the test ends and fakes do not leak across tests. *Check:* read. *Severity:* Minor. *Source:* GGB "Error handling in test helpers" (cleanup).
- **GO-TEST-18** [PREFER] Use `t.Context()` (Go 1.24 or newer) for a test's context, passed to helpers explicitly. *Why:* the context is cancelled when the test ends, before cleanup functions run, so test goroutines can be told to stop. *Check:* grep: `context\.Background\(\)` in `_test.go`. *Severity:* Minor. *Source:* REL124 (`T.Context`); GGD "Contexts".

- **GO-TEST-20** [PREFER] Put costly or failing setup in the tests that need it, not in `init()` or a package variable. *Why:* a run of one package should not pay for, or fail on, setup it does not use. *Check:* read. *Severity:* Minor. *Source:* GGB "Keep setup code scoped to specific tests".

- **GO-TEST-23** [MUST] Each test is independent of the others and restores any global or external state it changed. *Why:* leaked state makes tests order-dependent, which breaks filtered and parallel runs. *Check:* read. *Severity:* Major. *Source:* GGB "Keep setup code scoped to specific tests".
- **GO-TEST-24** [MUST] Each concurrent component has a shutdown test: start it, stop it, and assert that `Close` returns within a bounded time and that its goroutines have ended. - **GO-TEST-28** [MUST] Every goleak ignore option has a comment that names the goroutine's owner and why it may outlive the test. *Why:* a broad ignore hides the leak the check exists to find. *Check:* grep: `goleak\.Ignore`. *Severity:* Major. *Source:* GOLEAK `options.go`.
- **GO-TEST-29** [MUST NOT] A clean goleak run does not prove there is no leak. Also test that connections close and that queues stay bounded. *Why:* goleak sees goroutines only, not memory, files or connections. *Check:* read. *Severity:* Major. *Source:* GOLEAK `options.go`, `leaks.go`.
- **GO-TEST-30** [MUST] Run the race detector on the test suite: `go test -race ./...` in CI, for any change that touches shared state, goroutines or channels. *Why:* the detector finds the races that happen during a run, so an untested concurrent path is unverified. *Check:* `go test -race`. *Severity:* Major. *Source:* RACE "How To Use".
- **GO-TEST-31** [MUST] Concurrent tests really run the concurrent paths with several goroutines. A sequential test passes `-race` and hides the race. *Why:* the detector cannot see races in code paths that never run. *Check:* read; `go test -race`. *Severity:* Major. *Source:* RACE "How To Use" (the detector sees only paths that run).
- **GO-TEST-32** [MUST] The race detector needs cgo and a C compiler on the build host. CI runs race tests there, because a small device target may not be a supported platform. *Why:* a small device target may not support the race detector, so the check runs on the build host. *Check:* read the CI configuration. *Severity:* Minor. *Source:* RACE "Requirements".
- **GO-TEST-33** [PREFER] In a module whose `go` line is 1.25 or newer, test timers and background goroutines with `testing/synctest` instead of real sleeps. *Why:* inside a bubble the clock is virtual and advances when every goroutine is blocked, so timeout tests are fast and stable. *Check:* read. *Severity:* Minor. *Source:* REL125 "testing/synctest" (first in Go 1.24 behind `GOEXPERIMENT=synctest`).
- **GO-TEST-34** [MUST NOT] Do not `time.Sleep` in a test to wait for another goroutine. Wait on a channel, a `WaitGroup`, or a synctest bubble. *Why:* sleeps make tests slow and flaky under load. *Check:* grep: `time\.Sleep` in `_test.go`. *Severity:* Major. *Source:* GMM "Incorrect synchronization"; EXP.
- **GO-TEST-35** [PREFER] Before a change to concurrent code is committed, run the shutdown and leak tests with `-count` above 1, to catch a flaky wait. *Why:* a wait that is nearly always right can still fail under load; repeated runs expose it. *Check:* read. *Severity:* Minor. *Source:* EXP.

## GO-LIB: libraries and program setup

- **GO-LIB-1** [MUST] Define command-line flags only in `package main`. A library takes its configuration as arguments or struct fields, and importing a library registers no flags. *Why:* a library that registers flags makes every importer inherit surprise configuration. *Check:* grep: `flag\.(String|Int|Bool|Duration|Var)` outside `main`. *Severity:* Major. *Source:* GGD "Flags".
- **GO-LIB-2** [MUST NOT] Do not use `math/rand` (or `math/rand/v2`) to make keys, tokens, pairing codes or any secret; use `crypto/rand`. *Why:* a generator seeded from the clock has few bits of entropy. *Check:* grep: `"math/rand`; read the call sites. *Severity:* Major. *Source:* GGD "crypto/rand".
- **GO-LIB-3** [PREFER] Guard an expensive log argument behind an enabled check; `log/slog` offers `Logger.Enabled`. *Why:* a disabled log call should cost next to nothing. *Check:* read. *Severity:* Minor. *Source:* GGB "Logging errors" (cost of disabled calls); STD `log/slog` `Logger.Enabled`.
- **GO-LIB-4** [MUST] In a cobra command, take the context from `cmd.Context()`, not from a new `context.Background()`. *Why:* a fresh root context detaches the command from the cancellation that the framework provides. *Check:* grep: `context\.Background` inside command functions. *Severity:* Major. *Source:* GGB "Complex command-line interfaces" (applies only where cobra is used).
- **GO-LIB-5** [PREFER] Keep the command-line layer thin, so the driver is a library the CLI calls. *Why:* the CLI is just another client, so the driver can be tested without it. *Check:* read. *Severity:* Minor. *Source:* GGB "Complex command-line interfaces".
- **GO-LIB-6** [PREFER] Keep dependencies few, and do not rely on undocumented behaviour of a package. *Why:* fewer dependencies mean fewer code paths that can change behaviour. *Check:* read. *Severity:* Minor. *Source:* GGS "Least mechanism".

## Review order

For a review, check in this order and stop when the change is clean:

1. GO-CONC lifetimes, channel close, locks, and GO-EDGE device deadlines. A leak or a hang here stops the service.
2. GO-RES and the GO-EDGE bounds. Unbounded growth is the slow failure of a long-running process.
3. GO-ERR panic, exit and recover rules, and GO-CONC-10.
4. GO-TEST for concurrent code: the race run and the leak check are present.
5. The other areas, by the code they touch.

## Conflicts

1. **Black-box test packages.** GGS says black-box tests live in `<pkg>_test`; GGD prefers same-package tests by
   default. cv-kit: same package by default, `<pkg>_test` for tests that use only the exported API (GO-TEST-25).
2. **Recovering panics.** GGB says not to recover a panic just to keep running. A device service must keep serving
   other devices when one connection's frame is bad, and an unrecovered panic in any goroutine ends the program
   (SPEC). cv-kit: each long-lived goroutine recovers at its own top and stops or restarts only its unit of work
   (GO-CONC-10); library code never recovers to keep going (GO-ERR-21).
3. **Fatal exit.** The Google guides use a logging package's fatal exit in places. cv-kit: only `main` exits, and it
   exits with a message that says how to fix the problem (GO-ERR-23, GO-ERR-26).
4. **Third-party test tools.** GGD bans third-party testing frameworks and assertion libraries. cv-kit keeps goleak as
   a test-only leak check (GO-TEST-26) and does not adopt an assertion library. An equivalent leak check is acceptable.
5. **Atomics.** The uber guide uses a third-party atomic package. cv-kit uses the standard library's typed atomics
   (GO-CONC-39).
6. **Loop variables.** Older modules share one loop variable. cv-kit allows a capture only in a module whose `go` line
   is 1.22 or newer (GO-LANG-9).

## Not adopted

- Google-internal tooling: Bazel build stanzas, the internal `log` and `glog` APIs, the internal flag package, and
  Google's internal context-detachment package (GGD "Contexts", GGB "Program initialization" on the logging package).
- Protobuf-specific advice (import names with `pb`, message pointers): no protobuf is decided for this service.
- Third-party atomics and test libraries outside goleak (uber `atomic`, `go.uber.org/atomic`).
- Leap-second and time-library trivia (UBER "time"): no effect on a rule.
- Pure formatting that `gofmt` already decides (GGD "Cuddled braces", "Breaking long format strings").
- Google's advice to keep cancel-based tests on `context.Background()` when `t.Context` exists: superseded (GO-TEST-18).
- The memory model's semaphore example that takes the slot inside the goroutine (GMM): it limits running work but not the
  number of goroutines; GO-CONC-11 takes the slot before the `go` statement.
- The memory model's example that ends with an empty `select {}` (GMM): blocks `main` forever with no shutdown path.
- Effective Go's serving loops that ignore shutdown and its unbuffered reply channel: taught as ideas, unsafe as
  written; the corrected forms appear in GO-CONC-17 and GO-CONC-13.
- Race detector build tags that exclude racy tests (`!race`): they hide defects (RACE).
- Design advice on the Google "interfaces for RPC clients" pattern: it concerns RPC transports, not serial or raw sockets.

## Per-project settings and optional checks

- staticcheck's style checks (ST1000, ST1003, ST1016, ST1020, ST1021, ST1022) are off by default. Enable them in the
  project's config to check GO-NAME, GO-DOC and GO-IMP mechanically (GO-TOOL-5).
- goleak is a third-party test dependency. GO-TEST-26 accepts an equivalent leak check, so a project may choose
  another tool.
- The race detector needs cgo and a C compiler on the build host, and it is not used in the shipped binary (GO-RES-12).
